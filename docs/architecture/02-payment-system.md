# 02 — Payment System: Deep Dive & Continuity Plan

_This is the most important document in this set. Every workstream in [05-roadmap.md](./05-roadmap.md) that touches `app/Actions/Payment/**`, `app/Models/Transaction*`, `app/Models/PaymentMethod*`, `app/Console/Commands/PayPalFriendsFamilyScanReport.php`, or `routes/web.php`'s cron route MUST be read against this document first. The hard constraint for the whole modernization effort is: **the PayPal Friends & Family reconciliation path must keep working, without a gap, at every point in time, through every deploy.** It is currently the only way the business receives money (see KI-01)._

## 1. The two payment paths, precisely

### 1a. "Regular PayPal" — does not exist yet (KI-01)
`App\Actions\Payment\PayTransaction::handle(Transaction $transaction): void` is an empty method. No SDK, no webhook route, no seeded `PaymentMethod` row. **There is nothing here to "keep available" — it must be built.** Section 3 below covers how, and how to do it without risking section 1b.

### 1b. PayPal Friends & Family — the only live path
End-to-end flow:

1. **Order creation** (`OrderService::makeFromCart`) creates a `Transaction` with `state = initialized` and a generated `reference` (10 characters — `Transaction::REFERENCE_LENGTH`). The customer is told (via the order confirmation email/page) to send a PayPal Friends & Family payment to a configured PayPal handle/email (`PAYPAL_FF_EMAIL`/`PAYPAL_FF_HANDLE` env vars) and put that reference in the PayPal payment note, within 24 hours (per the copy seeded in `database/migrations/2022_09_25_032840_create_pay_pal_f_f_payment_method.php`) or the order is cancelled.
2. **Reconciliation is manual-trigger, batch, asynchronous**: an admin logs into PayPal's own website, exports a CSV of recent transactions (German-locale column headers — `Hinweis`, `Absender E-Mail-Adresse`, `Brutto`), and uploads it through `/admin/paymentMethods/upload` (`PaymentMethodController::uploadCsv`). The file lands in MinIO/S3 under `paymentMethods/paypal_ff/transaction_records_<timestamp>.csv`.
3. **The scheduler** — triggered only by an external HTTP pinger hitting `/{CRON_ROUTE}` (KI-03) — eventually runs `payment_methods:paypal_ff:scan-report` (`PayPalFriendsFamilyScanReport`), which lists un-processed files in that directory, parses each row, and calls `PayPalFriendsFamily\PayTransaction::handle($record)` per row:
   - validates the row has the expected amount/note columns, and that the note is exactly 10 characters (the reference length);
   - if the note fails that 10-char check specifically, falls back to `guessTransactionBasedOnNote()`, which looks at the sender's email, finds that user's pending orders, and fuzzy-matches by scanning the transaction's reference as a substring somewhere (comment recorded as "Matched based on note");
   - otherwise does an exact match: `Transaction` where `reference = Hinweis`, `state IN (initialized, ordered)`, `amount <= paid_amount`, oldest first;
   - on exact-amount match: marks `Transaction.state = paid`, `Order.status = paid`;
   - on overpayment: marks `Transaction.state = paid`, `Order.status = processing`, appends a "Customer paid too much!" comment for manual follow-up;
   - **on underpayment: nothing happens (KI-02)** — a gap to close, not a thing to "preserve."
   - every match attempt (success or not, once past validation) writes an audit `PartialTransaction` row with the raw CSV data.
4. Processed files move to a `processed/` subfolder so they are not re-scanned.

### Why "always available" is really about the scheduler, not the payment code
The actual payment-matching logic (`PayTransaction::handle`) only runs when something hits `payment_methods:paypal_ff:scan-report`, which only runs when something hits `/{CRON_ROUTE}`, which only happens if an external, unmonitored-from-inside-this-app HTTP pinger is alive and correctly configured. **The single highest-leverage availability fix in this entire system is KI-03** — moving scheduling inside the app's own infrastructure with real alerting, independent of any refactor to the payment logic itself.

## 2. Continuity rules for every change under this system

Any workstream touching payment code MUST follow these rules, enforced by code review (self- or peer-review — see [05-roadmap.md](./05-roadmap.md) risk tiers) before merge:

1. **Never change `PaymentMethod::CLASSMAP`, `PayPalFriendsFamily::ALIAS`, or any of its column-name constants in the same change that also changes `PayTransaction::handle`'s matching logic.** Rename/refactor and behavior-change are separate, separately-tested commits.
2. **Every change to `PayPalFriendsFamily\PayTransaction::handle` ships with a characterization test first** (a test that pins today's exact behavior, written *before* the change, run red-then-green against the old code to confirm it actually exercises the logic) — this is non-negotiable given this method currently has zero test coverage. See [03-testing-strategy.md](./03-testing-strategy.md) §1.
3. **Never deploy a change to the scheduler/cron mechanism (KI-03 fix) at the same time as a change to the reconciliation matching logic.** Cut over the delivery mechanism first, verify at least one real scheduled run succeeds end-to-end in production, then touch the matching logic in a separate deploy.
4. **Any schema migration touching `transactions`, `payment_methods`, or `transaction_partials` must be additive-only and backward compatible for at least one full deploy cycle** (add columns with defaults / nullable; do not rename or drop columns in the same release that also ships code depending on the new shape) — this is standard zero-downtime-migration practice and matters doubly here because the CSV-scan command runs asynchronously and unpredictably relative to a deploy.
5. **Before every deploy that touches anything in this document's scope, manually trigger `php artisan payment_methods:paypal_ff:scan-report` against a copy of the most recent real (or realistic synthetic) CSV export in a staging environment** and confirm it still matches/marks transactions correctly. This is the manual QA gate for this specific subsystem, on top of the automated test suite.
6. **Keep the F&F path and the new standard-PayPal path on fully separate `PaymentMethod::CLASSMAP` entries and fully separate Action classes** (already the existing shape — `app/Actions/Payment/PayPalFriendsFamily/PayTransaction` vs `app/Actions/Payment/PayTransaction`). Building standard PayPal must never require editing the F&F action class.

## 3. Building standard PayPal (new work, not a refactor)

_Design cross-validated against an independent architecture consultation (2026-10-16)._

**Approach: a thin client on PayPal's Orders v2 REST API, server-side redirect flow — not the JS Smart Buttons SDK, and not a third-party wrapper package.** The entire surface needed is four calls (OAuth client-credentials token, create order, capture order, verify webhook signature), small enough to hand-write against Laravel's `Http` facade and trivial to fake in tests. This deliberately avoids two worse options: PayPal's own official Checkout-PHP-SDK was archived in August 2025 and is explicitly deprecated with no further support; and a server-side redirect flow (create the order, redirect to PayPal's approve link, capture on return, treat webhooks as the source of truth) needs no JS on the checkout page, so the whole flow is coverable by ordinary `Http::fake()` feature tests rather than browser tests.

Concrete shape:
- Seed a `paypal` `PaymentMethod` row (`PaymentMethod::CLASSMAP` gets a second entry) with `enabled = false` from day one. Only an admin allowlist can select it until it has been exercised in PayPal's sandbox and then for a trial period in production.
- `App\Actions\Payment\PayPal\PayTransaction::handle()` (new file, mirroring the existing `PayPalFriendsFamily` action's placement convention — no existing F&F file is touched) creates the PayPal order with its `custom_id` set to the **same 10-character reference the F&F flow already generates**. This is deliberate: PayPal's own transaction export then carries that reference for standard payments too, so the *existing* CSV-reconciliation command becomes a free backstop for a lost or delayed webhook — one matcher, two payment methods.
- Webhook route: verify PayPal's signature, persist the raw event keyed by PayPal's event id (idempotent insert — PayPal retries webhooks for days), dispatch a queued job, apply the state transition only if not already applied for that event id. Handle at minimum `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.REFUNDED`, and `CHECKOUT.ORDER.APPROVED` (capture on approval even if the buyer never returns to the site after paying).
- **Unify the "mark paid" transition** so both payment methods call the same underlying state-transition code on `Transaction`/`Order` (never a second, parallel "mark paid" implementation) — this is also the natural place to fix KI-02 (underpayment) and KI-17 (money comparison) once, for both methods at once, if `PartialTransaction` genuinely represents "an amount applied toward a transaction" for both CSV rows and PayPal captures (confirm this reading of the model before relying on it; if it means something narrower, keep the two methods' partial-payment handling separate rather than forcing a shared model that doesn't fit).

**Incremental rollout without ever touching F&F**: write the shared-transition tests first (§ below) → build against PayPal sandbox credentials on staging, gated by the `enabled` flag → in production, enable for admins only, run one real small-value test ticket end to end, confirm the webhook arrives and the reference shows up correctly in a PayPal CSV export too → enable for everyone. Rollback at every step is flipping the `enabled` flag back off; F&F's code and data never change state.

**As built (Phase 5.4, 2026-10-16)**
- Config: `config/paypal.php`, env `PAYPAL_BUSINESS_MODE` (`sandbox`|`live`), `PAYPAL_BUSINESS_CLIENT_ID`, `PAYPAL_BUSINESS_CLIENT_SECRET`, `PAYPAL_BUSINESS_WEBHOOK_ID`; currency from `CURRENCY`. Deliberately separate from `PAYPAL_FF_*` (two accounts).
- Visibility: `payment_methods.admin_only` (new). `PaymentMethod::selectableBy($user)` is used by the checkout page and by `OrderCartRequest` validation: customers see `active && !admin_only`; admins also see `admin_only` rows. The `paypal` row is seeded `active=false, admin_only=true`. To go live: set `active=true, admin_only=false`. To roll back: `active=false`.
- Flow: checkout creates the order and transaction as before, then `StartPayPalPayment` creates the PayPal order (`custom_id` = the 10-char reference) and the customer is redirected to PayPal; `/paypal/return/{reference}` captures; the `CHECKOUT.ORDER.APPROVED` webhook captures too if the customer never returns. `PAYMENT.CAPTURE.DENIED/REFUNDED` only add a staff-review comment to the transaction.
- Idempotency: `transaction_partials.external_id` (the PayPal capture id, unique per transaction) makes the return capture, the `PAYMENT.CAPTURE.COMPLETED` webhook and webhook retries apply a payment exactly once; `paypal_webhook_events.event_id` is unique.
- Sandbox verification (2026-10-16, real PayPal sandbox, Business app credentials in the git-ignored local `.env`): OAuth token, create order (approval URL returned, `custom_id` = reference and amount round-trip on read-back, status `PAYER_ACTION_REQUIRED`) and webhook verification (a forged signature is rejected with `false`, so the controller answers 400) all work through `PayPalClient`. Still unverified against the sandbox: buyer approval followed by capture, and delivery of a real signed webhook (needs a sandbox buyer login and a public HTTPS URL registered for the webhook id).
- Config note: `CURRENCY` is blank in some `.env` files; `config/paypal.php` falls back to `EUR` in that case (a blank value would otherwise be sent to PayPal as the currency code).
- Known gaps: no "pay again" link after a cancelled or failed PayPal payment; unpaid PayPal orders keep transaction state `initialized` on purpose, so the existing 5-day reminder / 6-day auto-cancel job applies to abandoned PayPal checkouts exactly as it does to F&F ones (the reminder mail has PayPal-specific wording); the CSV backstop needs the Business account's export uploaded separately (the upload screen only handles F&F).

### Business/legal risk, not just a technical one
PayPal Friends & Family is against PayPal's terms of service for commercial sales, and is a common trigger for account limitation; a standard Business account (required to receive normal checkout payments) generally cannot also send/receive F&F. In practice this likely means **two separate PayPal accounts** (the existing personal/F&F one, and a new Business one for standard checkout) rather than one account doing both — a decision for you to make with PayPal directly, not something to assume away in the code. It is also one more reason to treat standard PayPal as urgent: the F&F account can be limited or frozen by PayPal at any time with no warning, and the reconciliation code should not assume a single receiving account is a permanent fact.

**DECISION (2026-10-16, owner): use two separate PayPal accounts** — the existing one stays dedicated to Friends & Family, and a new, separate PayPal Business account receives standard checkout payments. Consequences for Phase 5.4: the standard PayPal client's credentials (client id, secret, webhook id) must be their own config keys, never shared with or derived from anything F&F-related (`PAYPAL_FF_*`); the F&F CSV backstop only sees standard payments if the Business account's exports are uploaded to the reconciliation too, so that backstop needs its own report source rather than assuming one shared export. Opening the Business account (and getting its REST app credentials) is an external prerequisite for 5.5, not for building 5.4 against the sandbox.

### Webhook reachability
Webhooks need a publicly reachable HTTPS endpoint with a valid certificate (covered by the Kamal/`kamal-proxy` deploy design in [04-deployment.md](./04-deployment.md)). PayPal retries for days on failure, but a broken route silently drops money-state changes in the meantime. Mitigate with persist-before-process (above), plus a scheduled sweep for "orders approved but not captured in N minutes," plus the CSV-export backstop from the shared reference code.

## 4. Execution order (why this isn't "just start coding")

Payment availability decomposes into three independent things, all fragile today: the reconciliation *code* works, its *trigger* fires, and someone *notices* when either stops. The cheapest fix (noticing) should land first, because nothing else can be safely changed without the ability to see whether it broke something. Recommended order, each step gated on the previous one's tests/soak period:

1. **Safety net** — the characterization tests in [03-testing-strategy.md](./03-testing-strategy.md) item 1 (pinning today's reconciliation behavior, bugs included), the scheduler lock + dead-man's-switch preconditions, the KI-15 route-caching fix, and CI running all of it. Nothing below this point is safe to do without it.
2. **Scheduler cutover** (§2 above / [04-deployment.md](./04-deployment.md) §2) — replace the HTTP pinger with a real, monitored process.
3. **CI/CD pipeline** ([04-deployment.md](./04-deployment.md)) — image-per-commit, one-command rollback, *before* touching framework versions, so every later step has a safety net of its own.
4. **Framework/PHP upgrade ladder** ([05-roadmap.md](./05-roadmap.md) Phase 4) — one rung per deploy, each gated by a green payment suite and one real reconciliation run in production.
5. **Standard PayPal** (§3 above) — once the stack is modern enough that this isn't built on a foundation that's about to move underneath it.

If business pressure demands standard PayPal sooner than step 4 completes, it *can* move earlier (the thin `Http`-facade client works identically on Laravel 9) at the cost of carrying it through every deprecation sweep in the upgrade ladder — but it must not move ahead of steps 1-2, which are what protect Friends & Family while that work happens.
