# 03 — Testing Strategy

## Where we start from

Today the suite is effectively zero-coverage despite files existing (see [01-known-issues.md](./01-known-issues.md) KI-06, KI-07, KI-08): the one Dusk browser test that references a real model fatals on a missing `use` import, the one feature test with real assertions uses undiscoverable method names and a removed Laravel API, and the one "passing" unit test asserts `true === true`. `phpunit.xml` only registers `tests/Unit` and `tests/Feature` as suites — `tests/Browser` (Dusk) isn't even wired into a normal `phpunit` run. There is no CI to enforce any of this ever stays green.

## Tooling decision

_Cross-validated against an independent architecture consultation (2026-10-16), which changed the original recommendation here from "adopt Pest now" to "stay on PHPUnit now, switch to Pest later" — a sequencing correction, not a disagreement on the end state._

- **Write tests now as ordinary PHPUnit `^9.5.10` classes** extending Laravel's `TestCase` — the version already in `composer.json`, needing no dependency change to start. These run unchanged through every rung of the Laravel/PHP upgrade ladder in [05-roadmap.md](./05-roadmap.md).
- **Switch the runner to Pest 4 only once PHP reaches 8.3** (Pest 4 requires PHP 8.3+ and runs on PHPUnit 12 under the hood). Pest executes ordinary PHPUnit-style test classes side by side with its own syntax, so this is a one-PR runner swap with zero rewrite of existing tests — not a migration project. Adopting Pest on PHP 8.0/Laravel 9 today would mean fighting version constraints for a syntax preference with zero coverage benefit; not worth it at this stage.
- **Retire Dusk in favor of Pest 4's browser plugin (Playwright-backed) at the same PHP 8.3 rung**, rather than maintaining Dusk's ChromeDriver-version pinning in the meantime — Dusk stays for now (small smoke-test role only, see below) purely because it's already the installed dependency; don't invest further in it.
- **Laravel's HTTP testing (`tests/Feature`) is the primary workhorse** for controller/action-level coverage (cart, checkout, admin CRUD, the PayPal webhook receiver once built) — it exercises real routing/middleware/validation without browser overhead, and is what proves the server-side-redirect PayPal flow correct end to end with `Http::fake()`, with no browser needed for that part at all.
- **Run CI against a real MySQL 8 service container, not SQLite.** The reconciliation matcher's collation, `LIKE`, and decimal-string comparisons (see KI-17) behave differently on SQLite than on the MySQL this app actually runs on in production — a green SQLite suite would not have caught KI-17.

## Coverage order — payment-critical code first

Given the explicit constraint that payment reconciliation must never regress, testing work is sequenced to de-risk that first, not to maximize raw coverage percentage fastest:

1. **Characterization tests for the CSV/matching logic** (`PayPalFriendsFamily\PayTransaction::handle` and its private helpers), written against **real PayPal export files with names/emails scrubbed** — not synthetic fixtures invented from the parser's own assumptions, because the German-locale export's exact separator, `1.234,56`-style amount formatting, date format, encoding, and any BOM are precisely what breaks across PHP/locale changes and are what a hand-written fixture would silently get "right" by construction. Required cases: exact reference+amount match → paid; unparsable/short reference + sender-email fallback → paid; overpayment → flagged, not silently paid; **underpayment → first pin today's actual (broken) behavior, then add a second test proving the KI-02 fix**; **same amount, different decimal-place formatting (e.g. `"25,5"` vs a DB value of `"25.50"`) → must still match exactly, proving the KI-17 fix**; malformed row (missing column, non-numeric amount); unknown/no-match row → ignored, rest of file still processes; two pending orders with equal amounts and no usable reference → correctly fails to guess rather than guessing wrong; an already-paid order receiving a second payment → flagged, never silently re-applied; **the same CSV file processed twice end-to-end → identical final DB state** (this case is the precondition the scheduler cutover in [04-deployment.md](./04-deployment.md) depends on, since both the old and new trigger run briefly in parallel during cutover).
2. **Unit tests for the now-separated pure pieces** (reference generation, reference extraction from a noisy note, amount parsing/normalization, the match policy) — extracting these from the command into testable units is itself a refactor that must come *after* item 1 gives it a safety net, not before.
3. **Feature tests for the admin upload → command pipeline**: `PaymentMethodController::uploadCsv` stores to the configured disk correctly and only for an authorized (`payment_access` gate) admin; `PayPalFriendsFamilyScanReport` picks up a fixture CSV file from a faked storage disk (`Storage::fake(...)`), processes it, and moves it to `processed/`; the scheduler registration itself is tested (assert the task is registered with `withoutOverlapping()` and the dead-man's-switch pings, per [04-deployment.md](./04-deployment.md) §2).
4. **Feature tests for the full order lifecycle**: `CartController` add/remove/order, stock decrement under concurrent add (flagged as a needs-investigation risk in [05-roadmap.md](./05-roadmap.md) Phase 5.1), `OrderService::makeFromCart` creating the right `Order`/`OrderItem`/`Transaction` rows, sold-out rejection actually surfacing to the user (this test should fail today because of KI-05's redirect bug, now fixed — confirm it passes), order/transaction state-transition tests shared by both payment methods (write these **before** any standard-PayPal code touches that shared transition, per [02-payment-system.md](./02-payment-system.md) §3).
5. **Elapsed-time tests for order-finishing, payment-reminder, and orphan-cleanup logic**, using a fixed clock (`Carbon::setTestNow`) and asserting both directions of each comparison. This specifically guards the Laravel 11→12 upgrade rung in [05-roadmap.md](./05-roadmap.md): Carbon 3 (mandatory on Laravel 12) changes `diffInHours`/`diffInDays`/etc. to return **signed** floats instead of Carbon 2's absolute integers, which can silently flip the direction of an "older than X" check in exactly this kind of expiry/reminder logic.
6. **A small number of Dusk smoke tests** (retired in favor of Pest 4's browser plugin once PHP reaches 8.3, per the tooling decision above): full happy-path checkout through to the success page; sold-out ticket shows a visible error. Kept intentionally small — everything above this point is already covered by faster, more reliable feature tests; a browser test only adds value where there's real client-side JS, which this payment flow design deliberately avoids (see [02-payment-system.md](./02-payment-system.md) §3).
7. **Standard PayPal** (once built, see [02-payment-system.md](./02-payment-system.md) §3): `Http::fake()` feature tests for create→return→capture, a webhook with a bad signature rejected, a duplicate webhook event applied only once, a webhook arriving before the buyer's browser returns, and a `DENIED` capture — all before the `PaymentMethod` row is ever flipped `enabled = true`.
8. Everything else (admin CRUD for events/content/roles/etc.) gets ordinary feature-test coverage of the standard create/update/delete/list/authorization paths — useful, but explicitly lower priority than the items above.

**A pinned-bug test is still a test, and should say so.** Item 1's underpayment and money-comparison characterization tests will, before the fix lands, assert today's actually-wrong behavior on purpose (so the fix is provably a fix, not a guess). Name these tests so that's obvious (e.g. `test_underpayment_is_currently_silently_ignored_pending_KI02_fix`), and change one at a time, never bundled into a version-upgrade rung.

## Fixing the existing broken tests is not optional busywork

KI-06/KI-07/KI-08 are fixed as part of workstream setup, not left as "pre-existing failures to ignore" — a test suite with silently-undiscovered or fatal-on-run tests is actively worse than no suite, because it looks green while proving nothing. This is explicitly one of the first delegated workstreams in [05-roadmap.md](./05-roadmap.md) (already partially done — see Phase 0).

## CI enforcement

Every PR/push runs: `composer install`, `npm ci` (once the frontend pipeline from KI-14 is resolved), `./vendor/bin/pint --test` (static style check, already a dev dependency, currently unused), `php artisan test --testsuite=Unit,Feature` against a real MySQL 8 service container, and a separate, slower, optionally-non-blocking job for the Dusk smoke suite. See [04-deployment.md](./04-deployment.md) for the concrete Kamal-based pipeline design.

## Definition of done for "finish testing" (the user's ask)

Not "100% coverage" — that's not a meaningful target for a codebase this size and shape. Done means: every payment-state-transition branch in both PayPal paths has a passing test that fails when the branch's logic is reverted, backed by real (scrubbed) PayPal export fixtures for the reconciliation matcher specifically, given its criticality; the full order lifecycle has feature coverage; CI runs against real MySQL and blocks merges on red; and no test file in the repo is silently undiscovered or fatal when actually executed.
